# Daily-Use Audit — Avatar 26

## Persona

**Who:** A professional who uses Cortex sporadically — roughly once every two to three weeks. They have a vault with several active work projects registered, a growing `_changelog.txt` (50+ entries), and a backlog of unprocessed inbox items. They last touched Cortex on May 10, 2026 (22 days ago). Today they are opening Claude Desktop from their home directory to check project status, process a meeting note from last week, and log a decision from a call that happened while they were away.

**Mental model:** This persona does not remember which trigger phrases route to which skill. They have a vague sense that "Cortex knows things about my projects" but do not recall whether the tool requires explicit commands or operates silently. After 3 weeks, they half-expect to be greeted with a summary of what has changed.

## Day Narrative

### 9:12 AM — Opening Claude Desktop from home directory

The user opens a fresh Claude Desktop session. Their cwd is `~/` — not inside the vault, not inside any registered repo.

`session-start` fires → `boot-context.py` resolves `~/` against the registry, finds no match → **activation level L1 (Passive)**. The session block that arrives in context reads `Level: L1 — Passive` with no project context, just personality, the tail of memory.md (capped at 100 lines), and 15 lines of changelog.

Per `cortex-boot/SKILL.md` Step 3, L1 behavior is: "Say nothing. Answer the user's question directly." The user sees no greeting.

**What the user experiences:** They open Claude and get a blank prompt. After 3 weeks away, they have no sense of whether Cortex is active, what's in the inbox, or that three projects have open blockers. They type "hi" as a test. Claude says hi back. Cortex has said nothing.

**Friction point 1:** The user does not know if Cortex is loaded. The `cortex-session` block is in the system prompt, invisible to them. There is no ambient signal — not even an L2-style one-liner — because they are at L1. The inbox count (which `boot-context.py` reads at every level, `session-start` line 105: `lines.append(f"Inbox: {data.get('inbox_count', 0)} unsorted item(s)")`) is in the session block but Cortex never surfaces it at L1.

### 9:18 AM — Asking about project status

The user types: "what's the status of FKT?"

`user-prompt-submit` hook fires. Pattern match in `hooks/user-prompt-submit` line 149: `*"status of"*` → injects `<cortex-hint>likely-skill: cortex-check-status`. Good.

`cortex-check-status` fires. It calls `mcp__cortex-vault__read_hub` with the vault-relative path to the FKT project folder.

`read-hub.js` runs `extractBlockers(body)` (line 54–58), which looks for the `## Blockers` section with `- [ ]` checklist items. But the actual hub file — generated by `scaffold-project` using `assets/blank-template.md` — has a `## Open Questions & Blockers` pipe table, not a `## Blockers` section with checklists. `extractBlockers` returns an empty array. `extractOpenQuestions` also returns empty (it looks for `## Open Questions` checklist, not the pipe table).

**What the user experiences:** `cortex-check-status` reports "no open blockers" for FKT even though the hub has 2 open items in the `## Open Questions & Blockers` table. The user walks away with a false clean bill of health.

**Root cause evidence:** `assets/blank-template.md` line 70 defines `## Open Questions & Blockers` as a pipe table. `read-hub.js` lines 44–58 parse `## Open Questions` and `## Blockers` as separate checklist sections. These are incompatible formats. `boot-context.py` lines 205–224 correctly parses the pipe-table format (`## Open Questions & Blockers`) using regex + `cells[2]` for the type column — so boot-time blockers work, but the MCP tool `read_hub` used by `cortex-check-status` returns empty arrays.

### 9:35 AM — Processing a stale meeting note

The user has a Granola export sitting in their clipboard from a client call on May 28. They paste it — 40 lines, multiple `Speaker: text` labels.

`user-prompt-submit` fires. Lines 60–68: `LINE_COUNT >= 20` and `SPEAKER_COUNT >= 3` → routes to `cortex-process-meeting`. Structural trigger fires correctly.

`cortex-process-meeting` begins. It needs to call `thread_meeting` (MCP tool) to handle the `*Previous:*/*Next:*` links. The tool checks whether the series has 3+ notes (`thread-meeting.js` line 194): `if (effectiveGroup.length < 3)` → returns "Skipping". Since the user has been away 3 weeks, this may be the 2nd note in a series — below the threshold. The new note is created but not threaded.

The user is not told _why_ threading was skipped. The announce line from `cortex-process-meeting/SKILL.md` says "(first in this series)" for the no-thread case, but the threshold is 3 — so a 2-meeting series also silently skips threading. The user does not notice.

**Separately:** `cortex-process-meeting` hands off extracted decisions to `cortex-update-context`. That skill reads the hub via the MCP `read_hub` tool. It gets an empty blockers/open-questions array (same bug as above) — meaning it cannot check whether any decision contradicts an existing open question. The Conflict Rule (`cortex-update-context/SKILL.md` line 75) is effectively bypassed for open-questions conflicts because the read returns nothing.

### 10:05 AM — Logging a decision

User types: "we decided to move the Sage integration to phase 2 — log that"

`user-prompt-submit`: matches `*"we decided"*` line 92 → `cortex-update-context`. Hook fires correctly.

`cortex-update-context` proceeds. The post-tool-use hook fires on the `Edit` to the hub file, calling `reindex-one.js` in the background (`post-tool-use` lines 204–208). The reindex is backgrounded with `&` so it does not block the response. Good.

However: `post-tool-use` line 181 only has `PLUGIN_ROOT_FOR_CLI` set when `CLAUDE_PLUGIN_ROOT` or `CURSOR_PLUGIN_ROOT` is in the environment. In Claude Desktop, `CLAUDE_PLUGIN_ROOT` is set by the plugin runner. But the `APPEND_CLI` path (`mcp-servers/cortex-vault/bin/append-changelog-cli.js`) must exist on disk. If the user installed via the marketplace and the `bin/` directory was not bundled or was moved, `APPEND_CLI` will not be found and the fallback inline format is used — which differs from `changelog-format.js` format. The fallback at line 188–191 produces `ACTION [auto] | FILE: ...` without going through `formatChangelogEntry`, so the `VALID_ACTIONS` guard is bypassed.

### 10:30 AM — Asking "what happened while I was away?"

The user types: "what happened recently with my projects?"

`user-prompt-submit`: no pattern match (the phrase does not match any trigger in hooks lines 74–166). No hint is injected. Claude answers from its general context. The `Recent activity:` field in the `<cortex-session>` block is there (15 lines of `_changelog.txt` tail), but `cortex-boot` at L1 does not proactively surface it.

The user gets a generic "I can look into that for you" response. Nothing from the vault unless they ask something that explicitly triggers a skill.

**What would help:** A phrase like "what changed recently" or "catch me up" has no trigger-phrase row in `references/trigger-phrases.md`. This is the single most natural thing an infrequent user returning after weeks away would say. There is no routing for it.

### 10:45 AM — Session ends, memory flush

On session end, the `stop` hook fires. It checks `pending-memory.json`. If the session produced no explicit memory writes (likely — the user did not invoke `cortex-coach` or any skill that writes `pending-memory.json`), the stop hook exits after the signals check with `printf '{}\n'` (line 104–106). Memory is unchanged. The session's decisions went into the vault via `cortex-update-context`, but nothing about "FKT Sage integration moved to phase 2" lands in `memory.md` automatically.

After 3 weeks, `memory.md` still has only what was there on May 10. The decisions logged today exist only in project-level Changelogs, not in the cross-session memory that `cortex-boot` loads.

## Findings

### Finding 1 — read_hub parses a different hub schema than the template produces

**Severity: P0**

`read-hub.js` lines 44–58 parse `## Open Questions` and `## Blockers` as separate Markdown checklist sections (`- [ ] item`). The canonical project hub template (`assets/blank-template.md` line 70) defines `## Open Questions & Blockers` as a single pipe table. Every vault hub scaffolded from the template is invisible to `read_hub`. Both `cortex-check-status` (which calls `read_hub`) and `cortex-update-context` (which calls `read_hub` to check conflicts) will return empty blockers arrays for all real hubs.

`boot-context.py` lines 205–224 correctly parse the pipe-table format and do surface blockers at L3 boot — so blockers appear at session start, then disappear as soon as the user asks "what's blocking X?" in the same session.

**Fix:** Align `read-hub.js` to parse `## Open Questions & Blockers` as a pipe table matching the column layout from the template (columns: `#`, `Question / Blocker`, `Type`, `Owner`, `Status`). Parse as blockers any row where `Type` is `Dependency`, `Internal`, or `Unknown`, and `Status` is not `Resolved`.

### Finding 2 — No "catch me up" path for the returning user

**Severity: P1**

`references/trigger-phrases.md` has 22 routing rows. None of them match the natural language a returning user would use: "what happened recently", "catch me up", "what did I miss", "what's changed since I was last on". The L1 session block contains a `Recent activity:` field (15-line changelog tail) and an `Inbox:` count, but these are never surfaced unless a skill explicitly reads them.

The `user-prompt-submit` hook (lines 147–155) only matches `"what's the status of"`, `"what's the status"`, `"where are we on"` for `cortex-check-status`. A broader return-oriented query hits no match and returns `{}`.

**Fix:** Add a "recent activity / catch-me-up" trigger row to `trigger-phrases.md` and a corresponding pattern in `user-prompt-submit` (e.g., `*"what happened"*|*"catch me up"*|*"what changed"*|*"what did i miss"*`), routing to a lightweight status summary that surfaces inbox count, recent changelog activity, and any open blockers across all registered projects. Even an L1 one-liner noting "you have N inbox items and activity across M projects since you were last here" would dramatically improve the re-entry experience.

### Finding 3 — L1 boot is completely silent; inbox count and stale-vault indicators never reach the user

**Severity: P1**

`boot-context.py` reads `inbox_count` at every activation level. `session-start` line 105 injects `Inbox: N unsorted item(s)` into the session block. But `cortex-boot/SKILL.md` Step 3 for L1 says "Say nothing." Nothing in L2 behavior says to surface the inbox count either, unless there is a "stale blocker or urgent inbox item" (Step 3, L2: "one line max").

For a user returning after 3 weeks, `inbox_count` may be 5–10 and `changelog_total` may have grown significantly. There is no mechanism to detect "it has been N days since last session" and escalate to a brief re-entry notice. The session block does not include a `last_session:` timestamp, and `boot-context.py` does not compute one.

**Fix:** In `boot-context.py`, read the most recent line from `_changelog.txt` to derive `last_activity_date`. If today minus `last_activity_date` exceeds a configurable threshold (e.g., 7 days), set a `stale_vault: true` flag in the output. In `cortex-boot`, treat `stale_vault: true` as a reason to emit one passive line at L1 — even at passive level — e.g.: `It's been 22 days since your last session. You have 6 inbox items.` This is low-friction and gives the returning user orientation without over-provoking.

### Finding 4 — vault-path.txt session cache is never cleared between sessions; post-tool-use may target wrong vault

**Severity: P1**

`session-start` writes the resolved vault path to `$PLUGIN_DATA/session-cache/vault-path.txt` (line 44–45). The `stop` hook explicitly comments "leave other cache files intact" (line 188) and only removes `pending-memory.json` and `pending-signals.json`. `vault-path.txt` persists indefinitely.

`post-tool-use` reads `vault-path.txt` first; falls back to `config.json` only if the cache is empty (lines 69–88). If the user previously opened a session with vault A (perhaps a work vault), then opens a session with a different vault path configured (e.g., a personal vault), `vault-path.txt` still points to vault A. The new session-start will overwrite it — but only if the session-start hook fires and python3 succeeds. If session-start fails silently (python3 missing, boot-context.py crashes), `vault-path.txt` retains the old path. Any tool-use during the new session would then log changelogs to the wrong vault.

This is a real risk after 3 weeks away if the user upgraded their system, moved their vault, or reinstalled Python.

**Fix:** In `session-start`, explicitly truncate or remove `vault-path.txt` at the top of the script (before the python3 check), so any failure leaves the cache empty rather than stale. The fallback read from `config.json` is sufficient for robustness.

### Finding 5 — thread_meeting silently skips series with fewer than 3 notes; no user-visible reason

**Severity: P2**

`thread-meeting.js` line 194: `if (effectiveGroup.length < 3)` returns a skip message as the tool result — but the skip message is only visible in the raw tool output. `cortex-process-meeting/SKILL.md` says to note "(first in this series)" in the announce line, but does not distinguish between "genuinely first" (1 note) and "second in a two-meeting series" (2 notes, silently skipped). A meeting that is the second in a series gets no threading and no explanation.

For a returning user who has a two-meeting series (they attended a call on May 10, now processing May 28), the new note sits unlinked. In Obsidian, the notes are not discoverable via graph traversal. The user will not notice unless they manually check.

**Fix:** The threshold of 3 is reasonable as a heuristic (avoids threading one-offs), but the announce line in `cortex-process-meeting` should explicitly say "2nd in series — threading starts at 3 notes" rather than the current generic message. Optionally, lower the threshold to 2 with a flag so the user can opt in to threading from the second note.

### Finding 6 — check_dormant_features only tests for weekly_review; hardcoded string match is fragile

**Severity: P2**

`boot-context.py` lines 367–378: `check_dormant_features` checks `changelog_total >= 50` then searches the dormant list in `personality.md` for the literal string `"weekly_review"`. Only `weekly_review` triggers a feature suggestion — all other dormant features are silently ignored. The function returns a hardcoded string `"weekly_review may be ready to activate..."`.

For a returning infrequent user, `changelog_total` may be exactly 50–60 (at the threshold), and the feature suggestion fires every session for weeks until they act on it. There is no "seen" or "snoozed" tracking. The suggestion is queued (`cortex-boot` Step 4: "queue for next natural pause") but if the user never reaches that pause in the session, it fires again next time. It will appear to repeat indefinitely.

**Fix:** (a) Generalize `check_dormant_features` to iterate all dormant features from the YAML list, not just `weekly_review`. (b) Add a `last_suggested` timestamp to the dormant feature tracking (or a session-count guard in the feature suggestion output) so it does not fire every single session after the threshold is crossed. A simple "suggest at most once per 7 days" guard stored in `plugin-data` would suffice.
